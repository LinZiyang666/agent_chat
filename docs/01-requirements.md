# Agent Chat — 需求访谈（PM ↔ 客户）

> 形式：产品经理（Claude）逐轮提问，客户（用户）回答。
> 每轮访谈结束后，PM 在本文档**复述确认**已得到的结论，再开始下一轮。
> 目标：把"想要什么、为谁做、什么时候算成功"讲清楚，**架构与技术选型一律延后**。

---

## 访谈纪要

### 第 0 轮：已经明确的事（来自前面对话）

- 是一个**命令行工具**，用 Go 实现，最终用户通过命令行与系统交互。
- 系统包含三层：Discord（前端） → Discord Bot（中转） → Agent Gateway（核心）。
  *（注：这是用户最初提到的实现意向，本质上属于"解决方案"而非"需求"，需求访谈中会重新审视。）*
- 支持**不同身份的 bot 的增删改查**。
- 可以**拉起聊天群**。
- **Agent 有自己的生命周期**，对应的 bot 生命周期要和 agent 关联。
- **CLI 的主受众是 agent 本身**，agent 通过反复调用这个 CLI 来收发消息；同时人类也要能方便地用它来管理与使用。

> 上面这些更像"已经想到一半的方案"。下面的访谈是回到**用户真正想达成的事**。

### 第 1 轮：动机与场景（待客户回答）

PM 想先弄清楚两件事——**为什么**要做这个，以及**它跑起来之后到底是什么样**。

#### Q1.1 动机
你做这个工具是想达成什么？换句话说，如果半年后它运转得很完美，**世界上多了什么、少了什么**？
（例：方便我观察多个 agent 协作？让多个 agent 替我做某类任务？做研究实验？纯好玩？给团队/朋友用？……）

#### Q1.2 一个具体故事
能讲一个**最希望发生**的使用场景吗？越具体越好。
建议格式：
- **谁**（你 / 某个 agent / 路人甲）
- **在什么情境下**（早上起来 / 写代码遇到问题 / 半夜想找人聊天）
- **打开了什么**（Discord 客户端 / 终端）
- **做了什么 → 看到了什么 → 然后呢**

故事不需要完美，越像"日常一幕"越好。一两个就够。

#### Q1.3 为什么是 Discord
为什么选 Discord 作为前端？是因为：
- 你和 agent 都已经在 Discord 上活动？
- 想利用 Discord 的频道/语音/服务器体系？
- 朋友/团队都在 Discord 上？
- 只是觉得 Discord bot 好做？
- 其它？

这个答案会决定很多取舍，比如要不要支持语音、是否要绑定具体 guild、要不要做跨平台兼容。

## 结论汇总（按轮次累积）

### 来自第 1 轮（待用户确认）

**C1 项目定位**
- 用户正在构建一个更大的"**跨 agent 工作框架**"，整体形态尚未定型。
- 本项目 = 这个大框架的**通信组件**，是一个完整、独立的 CLI 工具。
- 类比：本 CLI 之于 agent = Discord 之于人类。Agent 把它当作"自己的通讯软件"使用。
- **明确不在本项目范围内**：
  - Agent 自身的逻辑生命周期（什么时候启动、停止、做什么任务）
  - Agent 怎么思考、怎么决策
  - Agent 框架本身的实现
- **明确在本项目范围内**：
  - 通信账号（"agent 在 Discord 上的身份"）的生命周期
  - 消息收发与状态管理
  - 群聊（chat room）的创建、成员管理、归档、删除
  - 与外界（其他 agent、人类、公告）沟通的所有渠道

**C2 通信能力对齐人类**
- 设计原则：**人类在 Discord 上能做的，agent 通过这个 CLI 也要能做**。
- 已点名的能力：发文字 / 发图片 / 接收文件 / @ 别人 / 回复消息 / 看历史。
- 推论：消息形态需要支持富内容（不只是纯文本）。

**C3 群聊（Chat Room）是核心抽象**
- 群聊由**人类**或**"系统管理 agent"**发起。  *(注：系统管理 agent 是什么，第 2 轮要追问)*
- 群聊把相关方拉进来（例：plan 制定者、审核者、其它实体）。
- 群聊是后续沟通的**持久承载体**（不是一次性的）。
- 群聊承载的是"项目级"的工作上下文（用户用 plan 评审举例）。

**C4 消息状态丰富**
- 不只是"收到一条消息"那么简单，消息有多维状态：
  - 已读 / 未读
  - 是否 @ 了自己
  - 是否被要求回复（要求 ack）
  - …(待补充)
- 这些状态是 agent 决定"我现在该不该回应"的关键输入。

**C5 通信账号的生命周期**
- 状态机草稿（待细化）：`创建 → 在线 → 离线 → 存档 → 删除`
- 这个生命周期与 agent 自身的逻辑生命周期**对应但不耦合**：
  - Agent 框架那边告诉本系统"这个 agent 活了 / 死了"
  - 本系统按指令把通信账号的状态切到对应位置
- Agent 在线时通过 background 进程 / Monitor 持续监听新消息。

**C6 选 Discord 的理由**
- 成熟的 bot 平台。
- 大部分功能免费。
- *(隐含)*：用户和 agent 都不需要再花成本造前端 UI。

### 来自第 2 轮（待用户确认）

**C7 角色模型：二元 + 身份无关（重要）**
- 系统只有两种角色：**管理员 (admin)** / **普通用户 (user)**，类 Linux 二元权责划分。
- **系统不区分账号背后是 agent 还是人类**。本系统就是一个"聊天 app"，用户是谁、怎么用，是 app 之外的事。
- 推论：所有对象（账号、群聊、消息）的设计都不应假设"agent 专属"或"人类专属"——一律按账号 + 权限处理。

**C8 与 agent 框架的对接（语义层面）**
- Agent 框架那边：负责管理 agent 的逻辑生命周期。
- 本系统这边：提供"账号"作为对接面——账号被 framework 创建/激活/停用/删除，对应 agent 的生与死。
- 具体怎么对接（CLI 调用 / API / 别的方式）→ **延后到架构阶段**。

**C9 聊天工具的纯粹性 + 资源映射**
- 本系统**不感知"项目"概念**——项目是 agent 框架的事，我们只做"聊天工具"。
- 群聊的语义是纯粹的："运维 agent 加入运维相关的群、像人一样工作"——账号订阅/加入/退出群，**至于群叫什么、为什么存在，本系统不关心**。
- Discord 资源映射：**所有群聊都在一个 Discord 服务器（guild）下**。本系统不处理多 guild 场景。

### 来自第 3 轮（待用户确认）

**C10 权限边界（最终形）**
- **admin**：拥有所有操作权限（账号 CRUD、角色变更、群 CRUD、邀请/踢人、改群名公告、归档/删除、看任何群历史、发系统公告……一票通过）。
- **user**：
  - 可以**查看系统公告**
  - 可以**查看自己订阅/所属群的聊天历史**
  - 可以**发消息**
  - （隐含）不能做以上之外的任何操作
- 推论：user 不能创建群、不能邀请人、不能踢人、不能看不属于自己的群——这些都是 admin 的事。

**C11 公告与提及（初稿，待澄清）**
- **群公告**：每个群有公告位，**user 也能发**（不限 admin）。
- **@all 提及**：可以让群内所有成员都被通知。
- ⚠️ **待澄清**：用户原话"就是所有都要"有两种理解——
  - (i) Q3.2 列的 a/b/c/d **全部**都要（群公告 + 全局广播 + 个体通知 + @all）
  - (ii) 只要"群公告 + @all"，"所有都要"指的是"@all 让群里所有人都收到"
  - 第 4 轮要确认。

### 来自第 4 轮（待用户确认）

**C12 公告体系（最终形）**
本系统有**三种** "对人喊一声" 的机制，语义彼此不同：

| 名称 | 谁能发 | 影响范围 | 语义 |
|---|---|---|---|
| **群公告** | 群成员都能发（user / admin） | 群内所有当前与未来成员 | 设置后，**新加入的成员必须读**（带"必读"语义）；老消息只是历史 |
| **@all 提及** | 群成员都能发 | 群内当前所有成员 | 一次性通知，老消息后续加入者不被强制读 |
| **系统公告** | 仅 admin | 全系统所有账号 | 全局广播 |

推论：
- "公告"不是单一概念，它在我们系统里有**强制读 vs 一次性提醒** 的差别。
- 必须有"消息是否已读完该群当前生效的群公告"这一状态。

**C13 订阅 vs 所属（语义二分）**
- **所属（membership）**：账号 ↔ 群之间的"成员"关系。
  - 所属 ⇒ 可以**查看该群的消息内容/历史**。
  - 不所属 ⇒ 看不到群内容。
- **订阅（subscription）**：账号 ↔ 群之间的"通知"关系。
  - 两个方向都存在：**主动订阅**（自己关注一个群） + **被订阅**（被加进通知列表）。
  - 订阅/被订阅 ⇒ 可以**收到该群的消息通知**。
- ⚠️ **待澄清**（第 5 轮 Q5.1）：
  - 所属是否默认带订阅？
  - 一个账号是否可以"订阅但不所属"（只收通知、看不到内容，比如管理员旁观）？
  - "被订阅"由谁触发——admin？群成员？任何人？

**C14 消息属性（最终清单 + 一项重大新需求）**
确认要的：
- 已读 / 未读
- 是否 @ 自己
- 是否要求回复（需要 ack）→ 进一步区分 **已回复 / 未回复**
- reply 关系（回复了哪条）
- 带附件（图片 / 文件）
- reaction
- 优先级（普通 / 紧急 / 系统）

明确不要的：
- 编辑过（**不实现**消息编辑）
- 撤回（**不实现**消息撤回）

**🌟 重大新需求：状态界面（State View）**
- Agent 不会逐条读所有消息，**主要看一个汇总状态**。
- 这个状态界面：
  - 是 agent 可"监听"的对象（具体监听形式留到架构）。
  - 汇总上面所有消息属性的当前态（哪些未读、哪些 @ 我、哪些待回复未回复……）。
  - 查看具体某条消息详情时，**这些属性也要一同展示**。
- 这是本系统对 agent 最重要的 UX 抽象——**优先级高，必须做**。

### 来自第 5 轮（待用户确认）

**C15 账号 ↔ 群 的三态关系**
基于 Q5.1 = B B A，账号对群的关系有 3 种：

| 关系 | 能看内容？ | 收通知？ | 出现在状态界面？ |
|---|---|---|---|
| **不所属** | ❌ | ❌ | — |
| **所属 + 未订阅**（旁观态） | ✅（主动进入查看） | ❌（不主动推送） | 出现在**次状态界面**（见 C16） |
| **所属 + 已订阅**（活跃态） | ✅ | ✅ | 出现在**主状态界面** |

操作规则：
- 加入群（所属）后**不会自动订阅**——两步独立动作。
- 订阅**必须先所属**（订阅 ⊂ 所属）。
- **被订阅** 操作只有 admin 能做（把别人加到某群的订阅列表）。
- ⚠️ **待澄清**：user 能否**自己主动**订阅"自己所属的群"？（Q5.1.3 只问了"被订阅"，主动订阅自己没问；按 admin/user 设计推断应该允许，但请第 6 轮确认。）

**C16 双状态界面**
**Agent 看到的是两个分层的视图**，不是一个：

- **主状态界面（Primary）**——展示"所属 + 已订阅"的群的全部汇总，包含全部 7 个维度：
  1. 总未读数
  2. 按群分组的未读数
  3. @ 我的消息列表（未处理）
  4. 要求我回复但未回复的消息列表
  5. 紧急 / 系统级消息单独区
  6. 新加入的群（带必读公告）
  7. 最近活跃群列表（按最后消息时间）

- **次状态界面（Secondary / 旁观）**——展示"所属但未订阅"的群的动态。
  - 默认不会主动推送给 agent。
  - Agent 想看时**主动进入**这个次界面查看。
  - 设计意图：让 agent 不被"我在群里但不关心"的群打扰，又不丢失这些群的存在感。

**C17 加群无上限**
账号可以加入任意多个群，无系统上限。

### 来自第 6 轮（待用户确认）

**C18 富消息与附件（纯文本工具 + 文件索引）**
本工具是**纯命令行**，**不做渲染**——输出统一为命令行文本，怎么呈现是用户（agent / 人）自己的事。

- **直接展示**（命令行可读）：纯文本、@提及、回复链、reaction、代码块（本来就是文本）。
- **不做的"花里胡哨"**：Markdown 渲染、链接预览、贴纸、投票、embed 卡片、视频/语音的播放……一律不做。
- **文件 / 图片 / 音视频**统一按"附件"处理：
  - 命令行只显示**索引**（文件名、大小、类型、本地路径、Discord 原始链接）。
  - 系统职责：**把 Discord 上的附件主动拉到本地**保存，维护本地索引。
  - 用户想看：自己拿索引去看（用本地任何工具打开）。
- **大小限制**：受 Discord 免费上限约束（当前 25MB / 文件）；超限的发送 → **直接报错**，不做切片、不做外链。
- 推论：本系统需要一个**本地附件存储区**（默认位置待定，配置可改）+ **附件索引表**（DB 中一条记录指向本地路径 + Discord URL）。

**C19 主动订阅 + 初始状态由 admin 决定**
- user **可以**自己 subscribe / unsubscribe **自己所属的群**。
- **初始订阅状态由 admin 在加群时决定**：admin 拉人入群时，有两种姿势：
  - 入群 + 不订阅（默认旁观态）
  - 入群 + 订阅（默认活跃态）
- 之后 user 自己想改，自己改。

**C20 历史保留：Discord 当云端 + 本地一致性**
- **Discord 是权威数据源**，长期存储靠 Discord，本系统不负责"永久保存全部消息"。
- 本地维护**缓存 + 索引**，覆盖以下能力：
  - 离线时仍能查最近聊过的内容
  - 知道"本地这条消息是否还和云端一致"——通过**哈希码 / 版本号 / 时间戳**之类的机制（具体形式留到架构）
  - 拉取增量时知道"哪些是新的、哪些可能变了"
- 推论：需要本地数据库（缓存消息 + 附件 + 状态）。

### 来自第 7 轮（待用户确认，访谈最后一轮）

**C21 多账号 + 会话级身份（重要约束）**
- 系统**不管单个 agent 持有几个账号**——那是 agent / framework 自己的事。
- **一次登录/会话只能登录并操作一个账号**（账号互斥的粒度是"会话"，不是"机器"）。
- **一台机器可同时跑多个 agent，使用多个不同账号**——所以**不能做机器级互斥**。
- 账号识别机制提示：**走环境变量 / 终端 / 会话上下文**（如 `AGENTCHAT_TOKEN` 之类），让每个 shell / 进程上下文绑一个身份。具体机制留架构。

**C22 离线全量补消息**
- 账号 offline 期间所属&订阅的群产生的新消息，**重新 online 时全部补拉**，不丢。
- 与 C20 联动：本地缓存必须能支持这种增量全量同步。

**C23 加入老群可看完整历史**
- admin 把账号加入有历史的群 → 该账号能看**加群前的所有历史**（对齐 Discord 默认行为）。

**C24 错误处理双轨**
- **(A) 命令级错误码**：CLI 每次命令出错都返回结构化错误码（按类别区分：鉴权失败 / Discord API 不可用 / 网络异常 / 速率限制 / ……），agent 可直接据此判断。
- **(B) 系统健康栏**：状态界面里**单独有一栏"系统健康"**，agent 监听这一栏可以持续感知 token / Discord / 网络的当前态。
- 两者**并行**——单次操作走 (A)，长期态势走 (B)。

## 访谈计划（PM 视角，可调整）

- **第 1 轮**：动机、典型场景、为什么是 Discord  ← 当前
- **第 2 轮**：用户与角色（人类参与度、谁有什么权限）
- **第 3 轮**：Agent 的"性格"与多样性（不同身份具体差在哪？人设？记忆？工具？）

- **第 5 轮**：规模与节奏（几个 agent / 几个房间 / 每天多少消息 / 跑多久）
- **第 6 轮**：质量与边界（延迟、可靠性、隐私、成本、消息留存）
- **第 7 轮**：MVP 边界（第一版必须有的 vs 锦上添花的）
- **第 8 轮**：成功标准（怎么判断"做成了"）

每轮以客户回答驱动，PM 可能根据答案插入临时追问轮次。
