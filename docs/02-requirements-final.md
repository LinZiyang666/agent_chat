# Agent Chat — 需求确认稿 v1.0

> 状态：**待用户最终确认**。本文档是 7 轮访谈（见 `01-requirements.md`）的最终归纳，是后续架构设计的**唯一需求基线**。任何后续讨论应引用本文档的条目编号。

---

## 1. 项目定位

### 1.1 这是什么
- 一个**纯命令行**的聊天工具，用 Go 实现。
- 它本身是一个 **完整、独立**的 app；同时是用户正在构建的"跨 agent 工作框架"中的**通信组件**。
- 它对自己的角色定位：**"agent / 人在 Discord 上聊天用的 IM 客户端"**。
- 类比：本工具之于 agent ≈ Discord 之于人。Agent 通过反复调用 CLI 完成"看消息、发消息、管群、看公告"等所有沟通行为。

### 1.2 这不是什么
- ❌ 不是 agent 框架本身。
- ❌ 不感知"agent 在做什么任务"、不感知"项目"等业务概念。
- ❌ 不内置 LLM 调用，不决定 agent 怎么思考、何时回复。
- ❌ 不做花哨的渲染（Markdown 渲染、链接预览、贴纸、投票、embed 卡片、视频/语音播放等一律不做）。
- ❌ 不实现**消息编辑**和**消息撤回**。
- ❌ 不做多 Discord 服务器（guild）管理——只对一个 guild 工作。

### 1.3 与"agent 框架"的边界
- **本系统**：账号生命周期、消息收发、群管理、附件、状态界面、本地缓存。
- **Agent 框架**（不在本项目范围）：agent 自身的逻辑生命周期、思考、决策、任务调度。
- 接口面：通过"**账号**"对接——framework 创建/激活/停用/删除账号，对应 agent 的生与死。具体接口形式留架构。

## 2. 角色与身份

### 2.1 角色（二元 + 身份无关）
系统只有两种角色：

| 角色 | 含义 |
|---|---|
| **admin** | 全权（Linux root 风格） |
| **user**  | 受限：看公告 + 看自己群历史 + 发消息 |

- **系统不区分账号背后是 agent 还是人**。所有对象都按"账号 + 权限"处理。
- 角色变更只能由 admin 操作。

### 2.2 账号与会话
- 系统**不管**一个使用者（agent / 人）持有几个账号——那是使用者自己的事。
- 单次登录/会话**只能登录并操作一个账号**。
- **一台机器可并发跑多个会话**（多个终端 / 进程 / agent 同时使用各自的账号），系统**不做机器级互斥**。
- 账号身份**绑定在会话上下文里**（环境变量等机制，具体形式留架构）。

## 3. 核心对象模型

### 3.1 账号（Account）
- 唯一身份。
- 字段（语义层面）：ID、名称、角色（admin/user）、Discord 端的对应 bot、生命周期状态。
- 生命周期状态机：

```
   ┌────────────┐
   │   created  │  framework 创建账号
   └─────┬──────┘
         │
   ┌─────▼──────┐
   │   online   │ ◀───────────┐
   └─────┬──────┘             │
         │                    │
   ┌─────▼──────┐             │
   │  offline   │ ────────────┘   （可往返）
   └─────┬──────┘
         │
   ┌─────▼──────┐
   │  archived  │   只读、不再收发消息
   └─────┬──────┘
         │
   ┌─────▼──────┐
   │  deleted   │   终态
   └────────────┘
```

### 3.2 群聊（Room）
- 在 Discord 上对应一个 channel（具体映射方式留架构）。
- 所有群聊都在**同一个 Discord 服务器（guild）下**——不做多 guild。
- 字段（语义层面）：ID、名称、当前群公告（带版本号）、成员列表、订阅者列表、创建时间、归档状态。
- 加群无上限：一个账号可以加入任意多个群。

### 3.3 消息（Message）
- 系统不实现**编辑**和**撤回**。一条消息发出后即不可改不可删（在本系统视角）。
- 消息属性（每条消息都有以下状态/字段）：

| 属性 | 含义 |
|---|---|
| 已读 / 未读 | 当前账号是否已读这条 |
| 是否 @ 自己 | 是否提及了当前账号 |
| 是否要求回复 | 是否需要 ack |
| 已回复 / 未回复 | 若要求回复，是否已回复 |
| reply 关系 | 是回复了哪条消息（threaded） |
| 附件 | 是否包含附件（图片/文件） |
| reaction | 表情回应（自己 + 别人的） |
| 优先级 | 普通 / 紧急 / 系统 |

### 3.4 附件（Attachment）
- 文件、图片、音视频统一作为"附件"处理。
- 命令行**不渲染**，只显示**索引**：文件名、大小、类型、本地路径、Discord 原始链接。
- 系统职责：把 Discord 上的附件**主动拉到本地**保存，维护索引。
- 用户想看：拿索引自己用本地工具打开。
- **大小限制**：受 Discord 免费上限约束（**当前 10 MB / 文件**；Discord 在 2024-09 把免费层从 25 MB 下调到 10 MB——`internal/api/v1/messages.go::DiscordAttachmentLimit`）；超限的发送 → **直接报错**（`ATTACHMENT_TOO_LARGE` → HTTP 413 / exit 22），不切片、不外链。运行在 Boost 等级 2/3 或 Nitro 的运营者可在源码里把常量 patch 上去。

### 3.5 公告（三种独立机制）

| 名称 | 谁能发 | 范围 | 语义 |
|---|---|---|---|
| **群公告** | 群成员都能发（user / admin） | 群内所有当前与未来成员 | 设置后**新成员必读**；老消息只是历史 |
| **@all 提及** | 群成员都能发 | 群内当前所有成员 | 一次性通知，后续加入者不被强制读 |
| **系统公告** | 仅 admin | 全系统所有账号 | 全局广播 |

衍生需求：必须有"账号是否已读完该群当前生效的群公告"这一状态。

## 4. 关系模型：账号 ↔ 群（三态）

| 关系 | 能看内容？ | 收通知？ | 状态界面归属 |
|---|---|---|---|
| **不所属** | ❌ | ❌ | — |
| **所属 + 未订阅**（旁观态） | ✅（主动进入） | ❌ | **次状态界面** |
| **所属 + 已订阅**（活跃态） | ✅ | ✅ | **主状态界面** |

规则：
1. 加群（所属）后**不会自动订阅**，两步独立。
2. 订阅**必须先所属**（不存在"只订阅不所属"）。
3. **被订阅**操作（把别人放进订阅）：**仅 admin** 能做。
4. user **可以**自己主动 subscribe / unsubscribe **自己所属的群**。
5. **初始订阅状态由 admin 加群时决定**（拉入群时可选"入群+订阅"或"入群+不订阅"）。

## 5. 关键能力

### 5.1 收发消息
- 收：账号 online 时持续接收所属群的消息（订阅与否仅影响通知，不影响是否收到）。
- 发：admin 不受限；user 只能在**自己所属的群**里发。

### 5.2 状态界面（核心 UX —— 对 agent 最重要）

**Agent 不会逐条扫消息，而是看一个汇总状态。** 这是本工具对 agent 最重要的抽象。

#### 5.2.1 主状态界面（Primary）
汇总"所属 + 已订阅"群的全部信息，包含 7 个维度：

1. 总未读数
2. 按群分组的未读数
3. @ 我的消息列表（未处理）
4. 要求我回复但未回复的消息列表
5. 紧急 / 系统级消息单独区
6. 新加入的群（带必读公告）
7. 最近活跃群列表（按最后消息时间）

外加 **第 8 个维度**（由 C24 引入）：

8. **系统健康栏**：token 状态 / Discord API 可达性 / 网络状态 / 最近错误摘要

#### 5.2.2 次状态界面（Secondary / 旁观）
- 展示"所属但未订阅"群的动态。
- **不主动推送**给 agent。
- Agent 想看时主动查询。
- 设计意图：让 agent 不被旁观群打扰，但仍保留这些群的存在感。

### 5.3 群操作
- 创建群、加人、踢人、改群名、改群公告、归档群、删除群 —— **仅 admin**。
- 自己 subscribe / unsubscribe 自己所属的群 —— **user 也可以**。

### 5.4 历史与一致性
- **Discord 为权威数据源**——长期存储靠 Discord，本系统不承担"永久保存所有消息"。
- 本系统维护**本地缓存 + 索引**，提供：
  - 离线时可查最近聊过的内容。
  - 一致性保证：通过**哈希码 / 版本号 / 时间戳**之类机制（具体形式留架构），知道本地内容是否与云端一致。
  - 增量同步：上线后能拉全错过的所有消息（C22）。
- **加入老群**：能看到加群前的完整历史（C23，对齐 Discord 默认行为）。

### 5.5 附件管理
- 系统主动从 Discord 下载附件到本地。
- 维护本地索引表：消息 ↔ 附件 ↔ 本地文件路径 ↔ Discord 原始 URL。
- 命令行展示时给出索引信息，用户自行打开。

### 5.6 错误处理（双轨）
- **(A) 命令级错误码**：每个 CLI 命令在失败时返回**结构化错误码**，按类别区分：
  - 鉴权失败（token 无效/过期）
  - 权限不足（user 试图做 admin 操作）
  - 找不到目标（账号/群不存在）
  - Discord API 不可用
  - 网络异常
  - 速率限制
  - 业务校验失败（如文件超大）
  - ……（详细枚举留架构）
- **(B) 系统健康栏**：状态界面里持续反映 token / Discord API / 网络的当前态，让 agent 监听长期态势。

## 8. 留待架构阶段决策（不影响需求语义）

这些是架构层面的选型/实现细节，需求阶段不决定：

1. CLI ↔ 后端服务的通信方式（gRPC / HTTP / 直接调本地进程 / 嵌入 daemon）。
2. 本地存储方案（SQLite / 文件 + 索引 / 其它）。
3. Discord 端的 bot 实现方式（独立 application / webhook / 混合）。
4. 状态界面的传输形态（轮询 / 长连接 / NDJSON 流）。
5. 哈希/版本号的具体形式（消息内容哈希 / Discord 自带 ID / 本地版本号）。
6. 附件本地存储位置与组织（默认目录、命名、清理策略）。
7. 错误码的具体枚举与编码规则。
8. 鉴权 token 的签发、轮换、撤销机制。
9. 速率限制 / 重试 / 退避策略。
10. 状态界面与 Discord 事件流之间的同步保证（at-least-once / exactly-once）。

## 9. 验收标准（成功画像）

需求做完之后，应该满足：

1. **一个 agent 进程**通过 CLI 可以完成全部沟通行为：发消息、看消息、看附件索引、监听状态界面、确认/拒绝回复要求、处理系统公告。
2. **一个人**也能用同一套 CLI 顺手地管账号、管群、看历史。
3. **同一台机器上多个 agent 并发** 各自使用各自的账号，互不干扰。
4. **离线 → 上线** 不丢消息，本地视图能恢复到与 Discord 一致。
5. **agent 不用关心 Discord 的存在**：所有 Discord 概念都被本工具屏蔽，agent 只看到"账号 / 群 / 消息 / 状态"。
6. **错误总有出口**：要么命令立即报错（错误码），要么系统健康栏反映长期问题。
